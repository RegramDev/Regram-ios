# 社群关联会话归档排查

2026-10-22，用户确认的现象是：带社群的群组或频道归档后，又回到主聊天列表。本轮以静态数据流审查及 arm64 编译为验证范围，按用户要求不运行功能、模拟器或真机测试。

## 原因与修改

归档入口通过 `updatePeersGroupIdInteractively` 写入归档分组，并产生 `SynchronizeGroupedPeersOperation`，发送 `folders.editPeerFolders`。服务端返回的 `folderId` 也会进入正常的状态重放。这条链路没有发现本轮问题对应的固定主列表写入。

固定主列表写入位于两条社群路径：

- `CommunityChatListSummary.swift` 的后台汇总在社群消息时间或汇总状态改变时，重新写入关联会话的 inclusion，并把 `groupId` 固定为 `.root`。它还会用创建时间重建最小时间戳，影响已有列表状态。这段成员重写在 b34621 的本机合并开关接入时加入。
- `Communities.swift` 的社群展开成功回调也把关联会话固定放到 `.root`。这条上游路径会影响从折叠状态恢复的已归档成员，不能只改后台汇总。

两条路径现均保留已有 inclusion，包括归档分组、置顶和时间信息。需要从隐藏状态恢复时，复用现有的 `loadAndStorePeerChatInfos` 读取服务端 dialog 的 `folderId`，不再推测它属于主列表。折叠、退出及不应显示的成员仍遵循现有排除规则。

读取服务端期间可能发生新的手动归档或取消归档，因此加入 `onlyRestoreMissing`：回写时在 Postbox 事务中再次确认目标仍然缺少 inclusion；已经有有效归属的会话不被这次补齐覆盖。该参数默认关闭，原有文件夹加载调用保持原行为。空列表直接完成，网络失败不创建猜测的主列表记录。

## 已核对的路径

| 路径 | 源码核对结论 |
| --- | --- |
| 侧滑、菜单及批量归档 | 共用引擎的分组变更与同步队列 |
| 取消归档与撤销归档 | 继续使用显式的主列表操作，不被社群补齐覆盖 |
| 服务端分组更新 | 正常重放保留返回的分组，同组时保留已有置顶及时间信息 |
| 群组／频道资料及成员更新 | `updatePeerChatInclusionWithMinTimestamp` 对已有 inclusion 保留其分组 |
| 社群汇总及启动后的汇总恢复 | 修正对有效归档的覆盖；缺失项按服务端实际分组补齐 |
| 社群折叠／展开 | 展开不再固定放回主列表；缺失项同样按服务端分组补齐 |
| 异步响应及失败 | 补齐仅应用于仍缺少 inclusion 的会话；网络失败不猜测取消归档 |

这些是源码审查结论，不是真实账号验收。没有操作用户的归档、账号或服务端数据，也没有批量迁移本地会话。旧版本已经错误移回的本地记录仍需由正常服务端同步纠正；本轮不会凭空猜测用户过去的归档选择。
