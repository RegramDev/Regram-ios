# b34661 主页过滤等待修正

用户在 b34660 中发现，广告已经从主页摘要消失，但正常消息迟迟没有补上。代码里存在两段串行等待：先判断所有会话的顶部消息，再读取纯广告会话的本地历史；找到正常回退后，又要等同批其他消息全部处理完才显示。因此模型已经给出有用结果，界面仍可能空着。

b34661 改为逐条通知当前列表。纯广告确认后即可读取本地历史，当前会话的回退候选紧跟它的顶部消息处理；正常摘要一旦确认，就先显示，其余会话继续判断。回退每次只扩展一条，同一相册仍作为整体处理，遇到正常消息便停止向更早处查找。

刷新在列表自己的队列上合并，间隔 50 ms；普通消息的完成不再依赖全局过滤通知。离开列表或收到新消息时取消旧请求，并拒绝晚到的历史查询结果。继续保留每次最多 16 个会话、每会话最多 50 条本地消息和最多 128 个会话的历史缓存限制。

这次没有更换 ReSieve 模型、调整阈值或提高推理并发。热状态、省电模式和后台暂停策略照常生效。未知候选不会被提前当成正常消息，媒体继承、原文恢复、草稿、排序和未读信息也沿用原有规则。

## 本地回归

使用生产桥接、预览代码和 SwiftSignalKit，设置一个纯广告会话及它的正常历史，再加入 24 个不相关会话。分类适配器为后者各增加 30 ms 延迟，用来暴露排队依赖，不用来评估模型速度。

修改前，正常摘要在约 4,176 ms 后显示，24 个不相关会话全部判断完才出现；修改后的一次对照中，约 213 ms 就显示，当时只处理了其中 2 个，全部完成仍需约 3,669 ms。测试断言是摘要必须先于剩余会话完成，同时所有会话最终仍被处理，不依赖某个毫秒阈值。

这些是 Mac 上人为延迟适配器的结果，不是 iPhone 速度，也不意味着整批模型推理快了相同比例。已有检查继续覆盖混合正文、实体与媒体、深层历史回退、相册、模型暂不可用、两个列表并行、取消请求和消息元数据；另补充历史查询晚于新消息返回的取消回归。86 项项目功能检查通过。
