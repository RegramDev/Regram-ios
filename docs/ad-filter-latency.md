## 为什么已有结果仍要等

原来模型推理、规则判断、样本记录和刷新计时器在同一条串行队列上。一个复杂消息正在推理时，后面的明确广告标签、已有缓存和已经到期的刷新都不能处理。普通结果还固定等待 1 秒；即使完全命中缓存，也要经过模型调度器的冷却间隔。

现在控制队列与推理队列分开。缓存、人工纠正、明确的整条广告标记先处理，每次最多 16 条、约 4 ms 后让出队列；单条规则判断仍有自己的预算，4 ms 不是抢占式期限。需要模型的消息才进入推理调度器，同一账号仍只允许一条推理在执行，继续保留公平调度、后台暂停和热状态／省电间隔。

混合消息可以先显示确定的裁剪，但在语义判断完成前不会被认定为可用的正常回退。临时裁剪不写成最终样本；最终判断先发布，再排队记录。已经显示的过滤结果不会因为随后离开页面而丢失记录。消息编辑、设置修改、人工纠正、取消或释放页面，会阻止晚到的旧结果写回页面和样本库。

刷新按 16–50 ms 合并，主页本地进度合并间隔为 16 ms。某个页面完成判断后，其他页面立即优先读取它的完整结果，不再被自己先前的临时裁剪挡住。样本页的模型预检和内存告警后的模型释放，也移到控制队列以外执行。

## 重复计算与内存

完整语义结果按精确输入复用，使用时仍重新应用当前规则及人工纠正。只缓存完成的模型结果，失败、超时和临时判断不能成为正常消息的缓存。后续优化将跨页面预算调整为显示结果 7 MiB、语义结果 512 KiB，另有条数上限，不跨账号共享。显示结果只放在内存；完整模型判断可以跨重启复用，文件只存带盐指纹、范围、概率等判断数据，不存消息正文。版本失效、容量和启动对照见[重启缓存记录](ad-filter-restart-cache.md)。

模型内部增加精确 token 窗口复用。只有输入 token 和由它生成的 attention mask 完全相同，才复用概率；没有缩短窗口、降低阈值或切换计算后端。字符串概率缓存与窗口缓存合计仍为 2 MiB。内存告警清空这些复用缓存；已取消的页面回调也及时移除。这里的预算是保留数据的估算值，不是整个进程的 RSS 上限。

## 验证与边界

排队回归使用生产桥接代码，把一条模型调用人为阻塞 700 ms，再提交明确标记的置顶广告。修改前，规则结果约 1412 ms、通知约 1433 ms；修改后多次运行都在阻塞模型结束前完成，规则结果约 1–5 ms、通知约 6–19 ms。同样的完整语义输入以新消息 ID 再次出现时，约 1–2 ms 完成，未增加模型调用。小于 1 ms 的读数按 `<1 ms` 理解。断言检查结果先后关系，不把机器负载下的某个固定毫秒值写成测试门槛。
